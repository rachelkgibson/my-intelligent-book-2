    Advanced Robot Programming

    Summary

    With deeper knowledge of sensors, control theory, and computing now in place, students return to robot programming for advanced techniques: teleoperation, robot motion programming, and path planning. The chapter covers control strategies for both robotic arms and wheeled robots, along with the practical skills of robot calibration, troubleshooting, and writing safety-conscious robot programs.

    From Driver's Seat to Autonomous Control: Why This Chapter Comes Now

    Now that you understand control loops in depth from Chapter 11: Control Systems and Feedback Loops, and know what is happening inside your microcontroller from Chapter 12: Digital Logic and Computing Fundamentals, it is time to put that knowledge to work in more sophisticated robot programs. Back in Chapter 4: Programming Your Robot, your programs were short scripts written before you understood setpoints, error signals, or the PID math that makes a real feedback loop stable. This chapter revisits robot programming with all of that theory already in hand.

    A real FTC competition match is split into two very different programming problems, and that split organizes this entire chapter. During the autonomous period, a fixed thirty-second window at the start of a match, the robot runs entirely on pre-written code with no human input at all. During the driver-controlled period that follows, a human operator steers the robot in real time using a gamepad, and the robot's program exists mainly to translate those button presses and joystick movements into motor commands. Every concept in this chapter falls on one side of that divide or the other, or bridges between them:

    • Human-controlled side: teleoperation and the robot interface that carries a driver's commands to the robot
    • Autonomous side: robot motion programming and path planning, which let the robot decide and execute its own movement
    • Shared, cross-cutting skills: wheeled and arm control strategies, calibration, troubleshooting, and safety programming apply to both halves of a match equally

    Teleoperation: Programming for a Human in the Loop

    Teleoperation is the practice of controlling a robot in real time from a distance, using a human operator's input device to command the robot's actuators moment by moment. In FTC, teleoperation happens during the driver-controlled period, when a student driver holds a gamepad and a program on the robot continuously reads that gamepad's state and converts it into motor and servo commands. Unlike the autonomous programs you will meet later in this chapter, a teleoperation program never decides on its own what the robot should do next; it simply repeats a fast, faithful translation loop for as long as the match clock runs.

    That translation loop follows a predictable pattern in almost every teleoperation program, regardless of what specific robot it controls:

    1. Read the current state of every input device (joystick positions, button presses, trigger values)
    2. Convert each raw input value into a meaningful command, such as a motor power level or a servo angle
    3. Send that command out to the appropriate actuator
    4. Repeat the entire cycle again immediately, often thirty to sixty times per second

    Notice how closely this mirrors the sense-decide-act cycle from Chapter 4's control loops, except the "decide" step has been handed almost entirely to the human driver. The program's real job is translation and safety-checking, not decision-making, which is exactly why teleoperation code tends to be shorter and more predictable than the autonomous code you will study next.

    Robot Interface: The Bridge Between Driver and Machine

    A robot interface is the combination of hardware and software that carries commands from a human operator's input device to the robot's microcontroller, and often carries status information back the other way. In FTC, the robot interface includes a wireless connection between a Driver Station tablet and the robot's control hub, a gamepad plugged into that Driver Station, and the software layer on the robot that reads gamepad values by name, such as gamepad1.left_stick_y for the left joystick's vertical position.

    A well-designed robot interface does more than pass raw numbers through unchanged. It maps physical inputs to logical robot actions in ways that make the robot predictable and comfortable to drive. The table below reinforces this mapping using vocabulary already introduced above, showing how one common gamepad layout might be assigned to a robot's actuators.

    Gamepad Input Raw Value Range Mapped Robot Action
    Left stick (vertical) -1.0 to 1.0 Forward/backward drive power
    Right stick (horizontal) -1.0 to 1.0 Turning rate
    Right trigger 0.0 to 1.0 Intake roller speed
    A button Pressed / not pressed Toggle arm servo between two preset angles

    Robot interface design also includes decisions about deadzone, a small range of raw joystick values near zero that the program treats as exactly zero, so a joystick that is not perfectly centered does not cause the robot to creep forward on its own. Building a deadzone into the interface layer is a small piece of code with an outsized effect on how controllable a robot feels to its driver.

    Robot Motion Programming: Moving Without a Human at the Wheel

    Robot motion programming is the practice of writing code that plans and executes robot movement without a human continuously supplying input, the defining skill of FTC's autonomous period. Where teleoperation translates a driver's joystick into motor commands moment by moment, robot motion programming must decide, entirely in advance or through sensor feedback alone, exactly how far to drive, when to turn, and when to stop.

    This distinction is important enough that it is worth seeing the two control flows side by side before moving further into either one.     Robot motion programming commonly relies on odometry, the technique of estimating a robot's position and heading by tracking wheel rotations over time, since an autonomous robot has no driver watching to correct its course. A basic autonomous motion program might command the robot to drive forward until an encoder reports 24 inches traveled, then turn 90 degrees, then drive forward again, chaining together simple moves into a complete routine.

    Path Planning: Deciding a Route Before Moving

    Path planning is the process of computing a sequence of positions or moves that will get a robot from its current location to a goal location, ideally while avoiding known obstacles. Robot motion programming, introduced above, focuses on executing a single planned move accurately; path planning operates one level higher, deciding what the full sequence of moves should be in the first place, especially when obstacles stand between a robot and its goal.

    A simple approach to path planning treats the robot's field as a grid of cells, some of which are blocked by obstacles, and searches for a connected sequence of open cells linking the start cell to the goal cell. The MicroSim below lets you experiment with exactly this kind of grid-based path planning yourself, placing a start point, a goal, and obstacles, and watching a simple search algorithm find a route around them.

    Real FTC autonomous routines rarely need a full search algorithm like the one above, since most fields have only a few known obstacles. Even so, the underlying idea, planning several moves ahead rather than reacting one step at a time, is exactly what separates a fragile autonomous program from a robust one.

    Wheeled Robot Control: Steering the Drivetrain

    Wheeled robot control is the set of programming techniques used to command a robot's drive motors so the whole chassis moves and turns as intended. The StarterBot chassis you built in Chapter 1 uses a drivetrain of Yellow Jacket gearmotors driving Gecko wheels, and the specific wiring of that drivetrain determines exactly which control technique applies.

    Two wheeled drive layouts appear most often in FTC robots, and each demands a different piece of control code. The comparison below reinforces terms already defined above and in Chapter 1, rather than introducing brand-new vocabulary.

    Drive Layout Wheel Arrangement Turning Method Can Strafe Sideways?
    Differential (tank) drive Left-side and right-side wheel pairs, each pair driven together Left and right sides run at different powers or opposite directions No
    Holonomic (mecanum) drive Four mecanum wheels, each with angled rollers Combining four independent wheel powers in different ratios Yes

    Differential drive is the simpler of the two to program: driving straight means commanding both sides to the same power, and turning in place means commanding the two sides to opposite powers. Holonomic drive trades that simplicity for maneuverability, since a program must calculate four separate wheel powers from just two joystick axes and a rotation input, but the payoff is a robot that can slide sideways without first turning to face a new direction. Whichever layout a robot uses, wheeled robot control code sits directly beneath both teleoperation and robot motion programming, translating whatever "move this way" command comes from above into the specific power sent to each wheel motor.

    Robotic Arm Control: Commanding Multiple Joints Together

    Robotic arm control is the set of programming techniques used to command a multi-jointed arm so its end effector, the tool or gripper at the arm's tip, reaches a specific position and orientation. Unlike a single drive motor that only needs a power level, an arm typically has several joints, each usually driven by its own servo or gearmotor, and all of those joints must be coordinated together to produce useful motion.

    Arm control programs typically work at one of two levels of abstraction, and recognizing the difference helps explain why some robot arm code looks far more mathematical than drivetrain code:

    • Joint-space control — the program commands each joint's angle directly, such as "set the shoulder joint to 45 degrees and the elbow joint to 90 degrees," leaving it to the programmer to know what combination of angles produces a useful arm position
    • Task-space control — the program specifies where the end effector should end up in real-world coordinates, such as "move the gripper to 30 centimeters forward and 20 centimeters up," and the code calculates the joint angles needed to get there using inverse kinematics, the mathematical process of working backward from a desired end-effector position to the joint angles that produce it

    Most classroom and early-competition FTC arms use joint-space control because it requires no extra math beyond commanding individual servos, the same basic servo-angle skill from Chapter 11's actuator control section. Task-space control and inverse kinematics become valuable once an arm has enough joints, or the required precision is high enough, that reasoning about individual angles by hand becomes impractical.

    Why Arm Control Feels Harder Than Drive Control

    A drivetrain has one goal at a time: a speed and a direction. An arm often has several joints that all affect the end effector's final position simultaneously, so a small change to one joint's angle can require compensating changes in the others. This is exactly why robotic arm control is usually taught after wheeled robot control rather than before it.

    Robot Calibration: Making Sensor Values Match Reality

    Robot calibration is the process of adjusting a robot's software so that its sensor readings and actuator commands correspond accurately to real-world physical values. A distance sensor fresh out of the box might report a value that is close to, but not exactly, the true distance in centimeters, and a drive motor commanded to "full power" on one robot might spin noticeably faster or slower than the identical motor on a teammate's robot due to manufacturing variation, wheel wear, or battery voltage.

    Calibration typically happens through a short, deliberate procedure before a robot's normal program runs, following a repeatable pattern:

    1. Place the robot or sensor in a known, measured condition (for example, exactly 20 centimeters from a wall)
    2. Record what the sensor actually reports in that known condition
    3. Calculate a correction factor or offset that converts the raw reading into an accurate real-world value
    4. Store that correction factor in the program so every future reading is automatically adjusted

    Skipping calibration does not necessarily make a robot's program crash, which is precisely what makes uncalibrated robots so frustrating to debug: the code runs without errors, yet the robot consistently stops two centimeters short of a wall or turns a few degrees past its intended heading, because every uncorrected reading carries the same small, silent error into every decision that program makes.

    Robot Troubleshooting: Diagnosing What Went Wrong

    Robot troubleshooting is the systematic process of identifying why a robot is not behaving as its program intends, and narrowing down whether the root cause is in the code, the wiring, the mechanism, or the calibration. Because a robot combines software, electronics, and moving mechanical parts, the same visible symptom, such as "the arm doesn't move," can trace back to causes in any one of those three domains.

    Effective troubleshooting follows a decision-tree pattern: start from an observed symptom, ask a series of narrowing questions, and arrive at a likely cause and fix rather than guessing randomly.     Robot Safety Programming: Designing Programs That Fail Safely

    Robot safety programming is the practice of writing robot code so that it behaves predictably and avoids harm even when sensors fail, communication drops, or an operator makes a mistake, rather than only handling the case where everything works perfectly. Every technique covered earlier in this chapter, teleoperation, motion programming, path planning, arm and wheeled control, calibration, and troubleshooting, becomes safer when it is written with this mindset from the start.

    A few safety programming practices show up repeatedly across FTC robots and industrial robots alike:

    • Timeouts — if an expected sensor reading or communication signal never arrives, the program stops the robot instead of waiting forever or assuming a default value
    • Range limiting — arm and servo commands are clamped to a safe range of angles in code, so a bug elsewhere in the program cannot command a joint past its physical limit
    • Emergency stop handling — the program checks for a stop signal on every loop pass, not just at specific points, so the robot can be halted immediately at any moment
    • Fail-safe defaults — if a control signal is lost mid-match, actuators default to a safe, stopped state rather than continuing their last command indefinitely

    Untested Code Is Not Safe Code

    A robotic arm that has never been tested near its full range of motion, or a drivetrain that has never been tested with a dead battery mid-command, has not actually been proven safe. Safety programming is validated through deliberate testing of failure conditions, not assumed from code that merely compiles.

    Robot safety programming is a fitting closing topic for this chapter precisely because it is not a separate skill practiced in isolation. It is a discipline applied on top of teleoperation, motion programming, path planning, arm and wheeled control, calibration, and troubleshooting alike, and the strongest FTC programs are the ones where every one of those techniques was written with failure, not just success, in mind from the very first line of code.

    Quick check: A student's autonomous path-planning routine finds a valid path around every obstacle on the field, but the student has never tested what happens if a wheel encoder wire comes loose mid-match. Which concept from this chapter is missing? Click to reveal the answer.

    Robot safety programming is missing. A correct path plan only describes the intended route; it says nothing about how the program should behave if a sensor it depends on fails partway through execution. A safety-conscious version of the same program would include a timeout or fail-safe default so a lost encoder signal stops the robot safely instead of driving on blind, incorrect assumptions.
