    Programming Fundamentals

    Summary

    Before students write a single line of robot code, this chapter builds general-purpose programming skills: algorithms, pseudocode, flowcharts, variables, data types, conditional statements, loops, functions, and debugging. Program testing and program security are also introduced. These concepts are taught independent of any particular hardware, so students can focus purely on computational thinking before applying it to their robot in the next chapter.

    Thinking Like a Programmer: What Is an Algorithm?

    Before you write a single line of code, you need a plan. An algorithm is a finite, ordered sequence of precise steps that solves a problem or completes a task, taking some starting information as input and producing a predictable result as output. Notice that this definition does not mention computers at all, because algorithms exist everywhere in daily life, not just inside a program.

    Consider a recipe for making a peanut butter and jelly sandwich. It has a clear starting point (two slices of bread and a knife), a clear sequence of steps (open the jars, spread the peanut butter, spread the jelly, put the slices together), and a clear ending point (a finished sandwich). A computer program's algorithm works the same way, except the "ingredients" are data and the "steps" are instructions a computer can carry out.

    For a sequence of steps to count as a true algorithm, and not just a vague suggestion, it generally needs to satisfy several properties:

    1. Finite — the algorithm must eventually stop; it cannot run forever
    2. Ordered — the steps happen in a specific, defined sequence
    3. Unambiguous — each step is precise enough that there is only one reasonable way to carry it out
    4. Has input and output — the algorithm starts with some given information and produces a result

    Throughout the rest of this chapter, one running example will appear again and again: an algorithm that checks whether a whole number is even or odd. It is simple enough to hold in your head, yet rich enough to demonstrate every concept from pseudocode through functions. Keep it in mind as each new tool for expressing and organizing algorithms is introduced.

    Expressing Algorithms Before Writing Code: Pseudocode and Flowcharts

    Programmers rarely jump straight from an idea to finished code. Instead, they first sketch the algorithm in a form that is easy to think through and easy to change, before worrying about the strict rules of any particular programming language. Two of the most common tools for this planning stage are pseudocode and flowcharts.

    Pseudocode is a way of describing an algorithm's steps using structured, plain language that resembles real code but does not follow the exact syntax rules of any specific programming language. Pseudocode lets you focus entirely on the logic of a solution, the order of decisions and repeated steps, without getting distracted by punctuation, spelling of commands, or which language you eventually plan to use.

    The pseudocode below describes the even-or-odd algorithm introduced earlier. Read it as a numbered set of plain-language instructions: it takes a number, divides it by 2, and checks whether anything is left over.

    1
2
3
4
5
6
7
    GET the number from the user
CALCULATE the remainder when the number is divided by 2
IF the remainder equals 0 THEN
    DISPLAY "The number is even"
ELSE
    DISPLAY "The number is odd"
END IF

    Notice that this pseudocode reads almost like an ordinary sentence, yet it is precise enough that any programmer, regardless of which programming language they prefer, could translate it into working code. That translatability is exactly why pseudocode is such a valuable planning tool.

    A flowchart is a diagram that represents an algorithm visually, using a small set of standardized shapes connected by arrows to show the exact order in which operations occur. Flowcharts use ovals for start and end points, rectangles for process steps (an action the algorithm performs), diamonds for decision points (a yes/no or true/false question that branches the flow), and arrows to connect everything in sequence. Because a flowchart is visual, it often reveals the branching structure of an algorithm, especially one full of decisions, more clearly than a written list of steps can.

    Pseudocode and flowcharts describe the exact same algorithm in two different formats, one written and one visual, and many programmers move back and forth between them while planning. Once the logic in either format feels solid, it is time to translate it into an actual programming language.

    From Plan to Code: Programming Languages and Syntax

    A programming language is a formal language with a defined vocabulary and grammar that a person uses to write instructions a computer can eventually carry out. Unlike the flexible plain language used in pseudocode, a programming language must follow strict, exact rules, because a computer cannot guess what a programmer "probably meant" the way a human reader often can.

    Hundreds of programming languages exist, including Python, Java, C++, JavaScript, and block-based languages that let programmers snap together labeled puzzle pieces instead of typing text. Despite looking very different on the surface, most of these languages can express the exact same underlying algorithm, including the even-or-odd logic from the pseudocode above.

    The table below shows that one algorithm, expressed three different ways: as pseudocode you already read, as text-based code in a Python-like language, and as the equivalent idea in a block-based language. Comparing them side by side highlights that the underlying logic never changes, only its surface appearance does.

    Representation How the "IF remainder = 0" step looks
    Pseudocode IF the remainder equals 0 THEN
    Text-based language (Python-like) if remainder == 0:
    Block-based language An "if" puzzle piece with an equals-comparison piece snapped inside it

    This strict set of rules that a language enforces, exactly how symbols, punctuation, spacing, and keywords must be arranged for a program to be considered valid, is called code syntax. Every programming language has its own syntax: Python requires a colon and consistent indentation after an if, while other languages require curly braces { } instead. A program that violates its language's syntax will not run at all, regardless of how correct its underlying algorithm is.

    Tip

    Almost every beginning programmer's first frustration is a syntax error, a missing colon, an extra parenthesis, a misspelled keyword. This is completely normal. Learning a programming language's syntax is a lot like learning the grammar rules of a new spoken language: frustrating at first, automatic with practice.

    Storing Information: Variables and Data Types

    Every useful program needs somewhere to keep track of information while it runs, whether that is a number a user typed in, a score, or a sensor reading you will meet in the next chapter. A variable is a named storage location in a program's memory that holds a value, and that value can change while the program runs, which is exactly why it is called "variable" rather than "constant."

    Returning to the even-or-odd example, the number a user provides needs somewhere to live while the program works with it. A programmer might create a variable named number to hold that value, and a second variable named remainder to hold the result of dividing by 2. Giving variables clear, descriptive names, number rather than a meaningless label like x1, makes code dramatically easier for other programmers, or your future self, to read and understand later.

    Not every variable can hold just any kind of value, however. A data type is a classification that tells the programming language what kind of value a variable holds and what operations can legally be performed on it. A variable storing a whole number behaves differently, and supports different operations, than a variable storing a sentence of text.

    The table below summarizes the four data types you will encounter most often, along with an example value for each, reinforcing the definition you just read rather than introducing anything new.

    Data Type What It Stores Example Value
    Integer A whole number, positive or negative, with no decimal point 7, -3, 1000
    Float (decimal) A number that includes a fractional, decimal part 3.14, -0.5
    String A sequence of text characters "even", "StarterBot"
    Boolean Exactly one of two values: true or false True, False

    In the even-or-odd example, the variable number would typically use the integer data type, since the algorithm is only designed to work with whole numbers. If a data type mismatch occurs, for example trying to divide a piece of text by 2, the program will usually fail with an error, which is one reason data types matter even though they can feel like an invisible detail at first.

    A few practical guidelines make variables easier to use correctly:

    • Choose a name that describes what the variable stores, such as remainder instead of r
    • Pick the data type that matches the kind of value the variable will actually hold
    • Avoid reusing the same variable name for two unrelated purposes within one program
    • Give a variable an initial value before using it in a calculation

    Controlling the Flow: Conditional Statements and Loop Structures

    So far, the even-or-odd algorithm has moved through its steps in a straight, single-file line. Most useful algorithms are not that simple; they need to make decisions and repeat work. Two structures make this possible: conditional statements and loop structures.

    A conditional statement is an instruction that tells a program to execute certain steps only if a specified condition is true, and optionally execute different steps if that condition is false. The even-or-odd pseudocode you read earlier already contains one: the IF the remainder equals 0 THEN ... ELSE ... structure is a conditional statement, branching the program down one of two paths depending on the result of a calculation.

    A loop structure is an instruction that repeats a set of steps multiple times, either a fixed number of times or for as long as a specified condition remains true. Suppose you wanted to check every number from 1 through 10 for even or odd, instead of just one number typed in by a user. Repeating the entire even-or-odd conditional ten separate times by hand would be tedious and error-prone; a loop structure lets the algorithm repeat the same logic automatically.

    The pseudocode below combines a loop structure and a conditional statement to check ten numbers in a row. Read it as: repeat the following steps once for each number from 1 to 10, and within each repetition, make the same even/odd decision as before.

    1
2
3
4
5
6
7
8
    FOR each number from 1 to 10
    CALCULATE the remainder when the number is divided by 2
    IF the remainder equals 0 THEN
        DISPLAY number, "is even"
    ELSE
        DISPLAY number, "is odd"
    END IF
END FOR

    Notice that the conditional statement inside this loop is identical to the one from the single-number version; the loop structure is simply what allows that same decision-making logic to run automatically ten times instead of once. This pattern, a loop that contains a conditional statement, is one of the most common building blocks in programming.

    Rather than only reading pseudocode, it helps to physically arrange these building blocks yourself and watch the resulting algorithm run step by step. The MicroSim below lets you drag conditional and loop blocks into a workspace, connect them in order, and press "Run" to see the resulting algorithm execute visually.

    Conditional statements and loop structures are two of the most powerful tools in any programmer's toolkit, precisely because so many real-world problems boil down to "make a decision" and "repeat something," combined in different arrangements.

    Organizing Code: Functions

    As algorithms grow larger, repeating the same block of logic by copying and pasting it everywhere becomes messy and hard to maintain. A function is a named, reusable block of code that performs a specific task, can accept input values called parameters, and can return a result, and can be called from other parts of a program whenever that task needs to happen again.

    The even-or-odd logic used throughout this chapter is a perfect candidate to become a function, since it might be needed in many different places within a larger program. The pseudocode below wraps that logic inside a function named checkEvenOdd, which accepts one input (a number) and displays whether it is even or odd.

    1
2
3
4
5
6
7
8
    FUNCTION checkEvenOdd(number)
    CALCULATE the remainder when number is divided by 2
    IF the remainder equals 0 THEN
        RETURN "even"
    ELSE
        RETURN "odd"
    END IF
END FUNCTION

    Once defined, this function can be called, or invoked, from anywhere else in the program simply by name, for example checkEvenOdd(7), without rewriting the underlying logic each time. Functions offer several concrete benefits to a program's design:

    • Reuse — the same logic can be called many times from different places without duplicating code
    • Organization — breaking a large algorithm into named functions makes the overall program easier to read
    • Easier testing — a small, isolated function is much simpler to test thoroughly than one giant block of code
    • Abstraction — a function lets other parts of a program use its result without needing to know exactly how it works internally

    You will use functions constantly once you begin writing real code, and in the next chapter, individual robot behaviors, like driving forward or checking a sensor, will often be organized as their own functions.

    Where You Write Code: Programming Platforms and IDEs

    Every program needs somewhere to actually be written, translated, and run. A programming platform is the combination of hardware and software environment where a program is written, is translated into a form the hardware understands, and ultimately runs. A programming platform might be an ordinary desktop computer, a web browser running JavaScript, or, as you will discover in the next chapter, a microcontroller platform built specifically to run inside a robot.

    Within a programming platform, most programmers do not simply type code into a bare text file. A programming IDE, short for Integrated Development Environment, is a software application that combines a code editor, tools that automatically highlight syntax errors, and a way to run or test the program, all within one convenient application. An IDE dramatically speeds up the process of writing, checking, and running code compared to switching between several separate, disconnected tools.

    The table below compares what a plain text editor offers against what a full programming IDE typically adds, since a table is well suited to comparing two options across a shared set of features.

    Feature Plain Text Editor Programming IDE
    Write code Yes Yes
    Highlight syntax errors automatically No Yes
    Suggest code as you type (autocomplete) No Usually
    Run or test the program with one click No Yes
    Built-in tools for finding bugs No Yes

    Choosing to write code inside a proper IDE, rather than a plain text editor, is one of the simplest ways to reduce frustrating syntax errors before a program is ever run. The next chapter introduces the specific programming platform and IDE you will use to write real code for your StarterBot, building directly on the vocabulary from this section.

    Making Sure Code Works: Debugging, Testing, and Security

    Writing an algorithm and translating it into correctly formatted code is only the beginning; real programs almost never work perfectly on the first attempt. The remainder of this chapter covers three closely related practices that professional programmers rely on constantly: debugging, program testing, and program security.

    Debugging is the process of finding and fixing errors, commonly called bugs, in a program's code so the program behaves as its algorithm intended. A bug can be a syntax error that stops the program from running at all, or something more subtle: a program that runs without crashing but produces the wrong answer, often because of a small mistake in a conditional statement or loop structure.

    Rather than only reading a description of debugging, it helps to practice spotting a real bug yourself. The interactive exercise below shows a broken version of the even-or-odd function from earlier in this chapter, with one line highlighted, and challenges you to identify the mistake before revealing the explanation.

    Finding and fixing one bug, however, does not guarantee a program is fully correct. Program testing is the practice of deliberately running a program with a variety of inputs, including unusual or extreme edge cases, to verify it produces the correct expected output before it is trusted or put into real use. A thorough tester of the even-or-odd function would not stop after trying the number 4; a complete test plan checks several different kinds of input:

    • Typical cases — ordinary numbers such as 4 or 7, to confirm the basic logic works
    • Edge cases — unusual boundary values such as 0 (which is even) or a negative number such as -2
    • Invalid input — values the algorithm was never designed to handle, such as text typed in instead of a number

    Skipping edge cases and invalid input is one of the most common reasons real programs fail unexpectedly once actual users, or in a future chapter, sensors and real-world conditions, start providing input the programmer never anticipated during initial testing.

    Beyond correctness, a finished program must also be trustworthy in a different sense. Program security refers to the practices and design choices that protect a program and its data from unintended misuse, unauthorized access, or malicious attack. Even a simple program that checks even or odd could be poorly secured if, for example, it crashed or behaved unpredictably whenever it received unexpected input, since predictable failure is itself a basic security concern.

    Warning

    Two beginner-friendly security habits are worth building now, long before you work with any sensitive data: never assume input will arrive in the exact form you expect, and always double-check any input before your program acts on it. A program that carefully validates its inputs, confirming a value really is a number before dividing it, is already practicing a basic form of program security.

    Debugging, program testing, and program security are not separate, one-time chores performed after "real" programming is finished. They are ongoing habits woven throughout the entire process of building any algorithm, from its first pseudocode sketch through its final, working code.

    Quick check: A loop repeats a decision-making step ten times, but the program only ever prints 'even.' What kind of concept from this chapter is most likely broken? Click to reveal the answer.

    Most likely a bug in the conditional statement, for example comparing the remainder to the wrong value or always following the same branch regardless of the calculated remainder. This is exactly the kind of mistake the "Spot the Bug" exercise in this chapter trained you to look for: a program that runs without crashing but still produces the wrong output.
