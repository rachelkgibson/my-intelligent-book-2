    Programming Your Robot

    Summary

    This chapter is where the robot comes to life. Students apply what they learned in Programming Fundamentals to the microcontroller that runs their StarterBot, learning what sensors and actuators are, the difference between open-loop and closed-loop control, and how a feedback loop and control loop work. Students will write their first robot programs: reading sensor input, commanding an actuator, and building a basic robot control loop capable of simple autonomous behavior.

    Microcontroller: Your Robot's Onboard Computer

    Every program you wrote in the last chapter, the even-or-odd checker included, ran on a laptop or desktop computer with a keyboard, a screen, and someone typing input by hand. A robot has none of those things sitting on its chassis, yet it still needs somewhere to run a program. That job belongs to a microcontroller: a small onboard computer, built directly into the robot, that loads your program, runs it continuously while the robot operates, and connects out to the robot's motors and sensors through wired ports.

    Think of the microcontroller as the StarterBot's brain, in the same practical sense that the chassis you assembled in Chapter 1 is its skeleton. In FTC robotics, this role is filled by a microcontroller-based control system, such as a REV Control Hub, mounted directly on the robot. Once you load your program onto it, the control system no longer needs a laptop connected to keep running; it executes your code on its own, reading sensors and driving motors in real time, the whole time your robot is powered on and competing.

    At this stage, you do not need to know how a microcontroller's internal circuitry works, that level of detail waits until a later chapter on digital logic and computing. For now, three practical facts are all you need to start programming:

    • The microcontroller stores and runs the program you write, step by step, exactly like a laptop runs a program, only smaller and built for a robot
    • The microcontroller has physical ports that motors, servos, and sensors plug into, so your code can send commands out and read values in
    • Once started, the microcontroller keeps running your program over and over, checking sensors and adjusting motors many times per second, without waiting for you to press a key

    That last fact is the single biggest difference between the programs you wrote in Chapter 3 and the programs you are about to write for a robot. A desktop program usually runs once, from start to end, and then stops. A robot's program, as you will see later in this chapter, usually runs its central logic again and again for as long as the robot is active.

    Sensors and Actuators: How the Robot Senses and Acts

    A microcontroller by itself cannot see, touch, or move anything; it only processes information. To interact with the physical world, it needs two categories of hardware plugged into its ports, and every piece of hardware on a robot falls into one or the other.

    A sensor is a device that measures some physical quantity in the real world, such as distance, light, or touch, and converts that measurement into an electrical signal the microcontroller's program can read as a value. An actuator is a device that takes a command from the microcontroller's program and converts it into physical motion or force, such as spinning a wheel or rotating an arm to a specific angle. In short: sensors carry information into the program, and actuators carry commands out of the program into the physical world.

    You have already met several actuators without calling them by that name. The StarterBot Kit you assembled in Chapter 1 includes two models of Yellow Jacket DC gearmotor, the 19.2:1 ratio (faster, lower torque, used for driving wheels) and the 50.9:1 ratio (slower, higher torque, used for mechanisms like the intake roller). It also includes Speed Servos mounted inside Compact ServoBlocks, which drive the Gecko wheels by rotating to a commanded angle rather than spinning continuously. Every one of these parts is an actuator: your program sends it a command, and it converts that command into real motion on the chassis in front of you.

    The base StarterBot build from Chapter 1 does not include any sensors, only actuators, which is exactly why its Chapter 1 behavior was limited to spinning wheels and rollers under direct human control. Later builds in this course, and real FTC competition robots, commonly add sensors such as a touch sensor (detects physical contact, reporting a simple pressed-or-not-pressed value) or a distance sensor (measures how far away the nearest object is, usually in centimeters). Once a sensor is added to the robot, its microcontroller program gains the ability to react to the world instead of only acting on it blindly, a distinction the rest of this chapter builds directly on.

    The table below reinforces the sensor-versus-actuator distinction using concrete StarterBot examples, so the difference is grounded in real hardware rather than an abstract definition alone.

    Category Direction of Information StarterBot Example
    Sensor Real world → program (input) A distance sensor added in a later build, reporting centimeters to the nearest object
    Sensor Real world → program (input) A touch sensor added in a later build, reporting pressed or not pressed
    Actuator Program → real world (output) Yellow Jacket 19.2:1 gearmotor driving a wheel
    Actuator Program → real world (output) Yellow Jacket 50.9:1 gearmotor driving the intake roller
    Actuator Program → real world (output) Speed Servo in a Compact ServoBlock driving a Gecko wheel

    Robot Programming: Applying Code to Real Hardware

    Robot programming is the practice of writing code that controls physical hardware, sensors and actuators, through a microcontroller, rather than only manipulating numbers and text on a screen. Every tool from Chapter 3, variables, conditional statements, loop structures, and functions, still applies directly. What changes is what the code is connected to and how it behaves once it is running.

    Three practical differences separate robot programming from the general-purpose programming you practiced in the last chapter:

    1. Physical units matter. A variable no longer just holds an abstract number; it might hold a distance in centimeters, a rotation in degrees, or a motor power expressed as a fraction of full strength.
    2. The program keeps running. Instead of executing once and stopping, a robot program typically loops continuously while the robot is active, checking sensors and adjusting actuators many times per second.
    3. The real world is unpredictable. A sensor reading can be noisy, a wheel can slip, and a battery can sag under load, so robot programs must tolerate imperfect, changing input in a way a simple even-or-odd checker never had to.

    With those differences in mind, robot programming for the StarterBot breaks down into two concrete skills you will practice for the rest of this chapter: reading values in from sensors, and sending commands out to actuators.

    Sensor Input Programming: Reading the Real World

    Sensor input programming is the specific skill of writing code that requests a current reading from a sensor and stores that reading in a variable so the rest of the program can use it. Just as GET the number from the user pulled a value into the even-or-odd program in Chapter 3, a robot program pulls a value in from a physical sensor instead of a keyboard.

    The pseudocode below reads a value from a distance sensor mounted on a future StarterBot build and stores it in a variable named distance_value, following the same plain-language pseudocode style used throughout Chapter 3. Read it as: ask the sensor for its current measurement, save that measurement, and then display it.

    1
2
    READ distance_value FROM the distance sensor
DISPLAY "Distance reading: ", distance_value, "cm"

    Notice that this pseudocode looks almost identical in structure to GET the number from the user from Chapter 3, except the source of the value is a physical sensor instead of a person typing at a keyboard. That similarity is intentional: sensor input programming reuses the exact same variable-and-input pattern you already learned, applied to a new kind of input source.

    A single sensor reading is rarely useful on its own; robot programs typically compare a sensor value against some meaningful number to decide what to do next. The list below gives a few concrete examples of comparisons a StarterBot program might make once a sensor is installed.

    • Compare a distance reading to a stopping threshold, such as 15 centimeters, to decide whether an object is too close
    • Compare a touch sensor's value to "pressed," to decide whether the robot has bumped into something
    • Compare two distance readings taken moments apart to decide whether the robot is getting closer to or farther from an object

    Actuator Output Programming: Commanding Motors and Servos

    Actuator output programming is the matching skill on the output side: writing code that sends a specific command to a motor or servo so it produces the intended physical motion. Where sensor input programming pulls a value in, actuator output programming pushes a command out.

    Different actuators expect different kinds of commands, which is an important practical detail before you write any actuator code. A Yellow Jacket DC gearmotor is typically commanded with a power level, a fraction between full reverse and full forward, such as 0.6 for sixty percent of full forward power. A Speed Servo, by contrast, is typically commanded with a target angle in degrees, since a servo's whole design is built around rotating to and holding a specific position rather than spinning freely.

    Actuator Type Command Style StarterBot Example
    DC gearmotor (Yellow Jacket) Power level, a fraction such as -1.0 to 1.0 Drive gearmotor commanded to run at 0.6
    Servo (Speed Servo) Target angle, typically 0-180 degrees Gecko wheel servo commanded to angle 90

    The pseudocode below commands both actuator types found on the StarterBot: a drive gearmotor set to a power level, and a Gecko wheel servo set to a target angle. Read it as two separate, direct commands sent out to two different physical parts.

    1
2
3
    SET drive_power TO 0.6
COMMAND left_drive_motor TO RUN AT drive_power
COMMAND wheel_servo TO MOVE TO ANGLE 90

    Sensor input programming and actuator output programming are the two building blocks every robot program is constructed from. On their own, though, they describe two separate, disconnected actions. The next two sections explain what happens once those building blocks are combined, and why that combination is the single most important idea in this chapter.

    Open-Loop Control vs. Closed-Loop Control

    Open-loop control is a control strategy in which the program sends a command to an actuator without ever checking the actuator's actual result against a sensor. The command is sent, and the program moves on, regardless of what actually happens in the physical world. Closed-loop control is a control strategy in which the program continuously checks a sensor's reading and adjusts its actuator commands based on that reading, correcting its behavior as conditions change.

    An open-loop drive command might look like the pseudocode below: drive forward at a fixed power for a fixed amount of time, with no sensor involved at all.

    1
2
3
    COMMAND drive_motor TO RUN AT 0.5
WAIT 3 seconds
COMMAND drive_motor TO RUN AT 0

    This open-loop code has an obvious weakness: it has no way of knowing whether the robot actually traveled the intended distance, or whether it stopped early after hitting a wall, or drifted off course because one wheel slipped on the floor. A closed-loop version of the same task would instead check a distance sensor while driving and stop only once the sensor reports the robot is close enough to its target, adjusting automatically to real conditions instead of blindly trusting a fixed time delay.

    The following table summarizes the practical trade-off between the two strategies, since a StarterBot program will use both approaches at different times depending on whether a relevant sensor is available.

    Control Type Uses Sensor Feedback? Adapts to Real-World Conditions? Example
    Open-loop control No No Drive forward for a fixed 3 seconds
    Closed-loop control Yes Yes Drive forward until a distance sensor reads less than 15cm

    Because the difference between these two strategies is really about how information flows, whether a sensor's reading loops back to influence the actuator command or not, it is worth exploring that flow visually before moving on.     Tip

    Open-loop control is not automatically "wrong." Turning on an intake roller for a fixed match duration, with no sensor involved, is a perfectly reasonable open-loop design. Closed-loop control earns its added complexity specifically when a task's outcome depends on unpredictable real-world conditions, such as exactly how far away a wall happens to be.

    Feedback Loops and Control Loops: Sensing and Acting Together

    The closed-loop example above depends on a specific pattern repeating over and over: read a sensor, decide what to do, act, and then read the sensor again to see the effect of that action. This repeating pattern has its own name at two related levels of description.

    A feedback loop is the general cycle in which the outcome of an action is measured and that measurement is used to influence the next action, a concept that applies far beyond robotics, from a thermostat adjusting a furnace to a driver steering a car based on where the road appears to be heading. A control loop is the specific, repeating sequence of steps, typically sense, decide, and act, that a program executes over and over to implement a feedback loop in software. In short: a feedback loop is the underlying idea, and a control loop is how a program actually carries that idea out, one repetition at a time.

    Because a control loop's three stages, sense, decide, and act, always feed into one another in the same repeating order, this cycle is often drawn as a simple looping diagram. Explore the diagram below to see how each stage connects to the next, and click each stage to review its definition before you meet the StarterBot's own control loop in the next section.

A control loop is simply a loop structure whose body contains a sensor read, a conditional decision, and an actuator command, applied specifically to robot hardware.

    The Robot Control Loop and Autonomous Behavior

    Everything in this chapter comes together in one final concept. A robot control loop is the specific control loop that runs continuously on a robot's microcontroller while it operates, combining sensor input programming, a decision step, and actuator output programming into one repeating cycle written directly in the robot's program. Where "control loop" describes the general sense-decide-act pattern, "robot control loop" refers to that same pattern implemented as real, running code on a specific robot's microcontroller.

    The pseudocode below implements a robot control loop for a StarterBot equipped with a distance sensor, using a loop structure and conditional statement in exactly the style you practiced in Chapter 3. Read it as: keep repeating this cycle while the robot is active, checking distance on every pass and adjusting the drive motor accordingly.

    1
2
3
4
5
6
7
8
9
    SET stop_threshold TO 15
WHILE autonomous_period_active
    READ distance_value FROM the distance sensor
    IF distance_value > stop_threshold THEN
        COMMAND drive_motor TO RUN AT 0.5
    ELSE
        COMMAND drive_motor TO RUN AT 0
    END IF
END WHILE

    This robot control loop drives the robot forward as long as the wall ahead is farther away than the 15-centimeter threshold, and stops the drive motor the moment the sensor reports the robot has gotten close enough. Every pass through the WHILE loop repeats the same sense-decide-act cycle from the diagram above: read the sensor, decide with the IF statement, and act with the COMMAND.

    A robot control loop like this one is also what makes autonomous behavior possible. Autonomous behavior is a robot's ability to sense its surroundings and choose its own actions using its program's control loop, without a human operator continuously steering it in real time. This stands in direct contrast to driver-controlled operation, where a person continuously sends commands, for example through a joystick, and the robot has no need to decide anything for itself. In FTC competition, this distinction matters enough that matches are split into a short autonomous period, where robots run their own control loop with no driver input, and a longer driver-controlled period afterward.

    Success

    Once you can write a robot control loop, you have everything you need for basic autonomous behavior: a sensor reading feeding a decision, and a decision driving an actuator, repeating on its own without a driver's joystick. Every later chapter on sensors, control systems, and advanced robot programming builds directly on this one repeating pattern.

    Quick check: A student writes a program that commands the drive motor to run for exactly 3 seconds and never reads any sensor. Is this open-loop or closed-loop control, and what concept from this chapter would you add to make it closed-loop? Click to reveal the answer.

    This is open-loop control, since the command is sent without ever checking a sensor's reading, and the robot has no way to adjust if conditions differ from what was expected. To make it closed-loop, you would add sensor input programming, for example reading a distance sensor, and wrap the motor command in a conditional statement inside a loop structure that keeps checking the sensor and adjusts or stops the motor based on its reading, forming a robot control loop.

    You now have a working vocabulary and pseudocode pattern for programming a real robot: the microcontroller that runs your code, sensors and actuators as the two categories of hardware it connects to, the sensor input and actuator output programming skills that read and command that hardware, and the open-loop, closed-loop, feedback loop, and control loop concepts that describe how a program can react to the world instead of only acting on it blindly. The robot control loop and autonomous behavior introduced at the end of this chapter are the exact building blocks every later chapter on sensors, control systems, and advanced robot programming will expand on, using the same StarterBot sitting on your workbench.
